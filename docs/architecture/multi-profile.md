# Multi-profile isolation model

The repo runs more than one candidate from a single engine. The rule
that makes this work is "profile is data; engine is service." Engine
code never knows a candidate's name, company list, or resume content;
it loads those from `profiles/<id>/` at the start of each invocation
and treats them as inputs.

The two live profiles today are PM-Pete (a senior PM searching for AI
PM roles) and Healthcare-Hannah (a healthcare professional searching
for clinic-side roles). They share the same engine binary; their data
trees, Notion workspaces, and secret keys are fully separate. The
engine has no concept of either persona — it sees `profile_id` strings
like `jared` and `lilia` and routes I/O accordingly.

## Per-profile directory layout

```
profiles/<id>/
  profile.json                # identity, modules, Notion DB ids, fit prompt
  filter_rules.json           # title / company / location blocklists (flat shape)
  resume_versions.json        # archetypes -> resume DOCX content blocks
  cover_letter_versions.json  # archetypes -> CL content blocks
  cover_letter_template.md    # template with {{placeholders}}
  applications.tsv            # canonical pipeline state (v2 schema)
  resumes/                    # generated DOCX + PDF artifacts
  cover_letters/              # generated PDF artifacts
  application_answers/        # per-application Q&A captures
  .gmail-state/               # gitignored: check_context, raw_emails, processed_messages
  .stage18/                   # gitignored: onboarding wizard state
```

The first six files are the only ones an operator authors (or has
generated by the Stage 18 wizard). Everything else is engine-managed.
Profile directories outside `profiles/_example/` are gitignored — the
example directory ships a synthetic, PII-free template for new users.

## Per-profile secret namespacing

All secrets live in the root `.env`, namespaced by uppercase profile
id. `engine/core/profile_loader.js` (`loadSecrets`) reads only the keys
that match the active profile's prefix. With `--profile jared`,
`LILIA_*` variables are never loaded into process memory.

```
JARED_NOTION_TOKEN=...
JARED_USAJOBS_API_KEY=...
JARED_USAJOBS_EMAIL=...
LILIA_NOTION_TOKEN=...
```

The engine never prompts for secrets. Onboarding instructs the operator
to add them to `.env` directly; the loader fails fast if a required
key is missing for an enabled module.

## Shared master pool

`data/jobs.tsv` and `data/companies.tsv` are the only cross-profile
artifacts. They are gitignored and contain dedup keys plus ATS slugs —
no PII, no resume content, no salary preferences. Their role is purely
to suppress duplicate API calls when two profiles scan the same
Greenhouse / Lever / Ashby slug.

If PM-Pete's scan discovers a new vendor, the company row lands in
`data/companies.tsv` and Healthcare-Hannah's next scan can use it for
adapter selection. Whether the row also enters her `applications.tsv`
is a separate question decided by her `filter_rules.json` — discovery
is shared, application state is not.

## Notion isolation

Each profile owns:

- A workspace page (parent for all profile-side Notion content).
- A Jobs Pipeline DB (per-profile schema with feature gating; the
  Stage 18 wizard's `property_map.js` decides which optional groups
  are included).
- A Companies DB (per-profile because tier classifications differ —
  what's tier S for PM-Pete is irrelevant to Healthcare-Hannah).
- Optional aux DBs: Application Q&A and Job Platforms.

Profile A cannot read or write Profile B's Notion content. The
isolation is enforced by the secrets layer: each profile carries its
own integration token; tokens are scoped to the profile's workspace
page at provisioning time.

## Engine selects profile via `--profile <id>`

Every command requires `--profile`. There is no implicit default. The
loader validates the id with the regex `^[a-z][a-z0-9_]{1,31}$` and a
reserved-name list (`example`, `default`, `test`, etc.) before any
filesystem access. After validation it `path.resolve`s the profile
root and asserts the result is strictly inside the `profiles/`
directory — preventing `../` traversal even if a misconfigured CLI
caller passes a literal slash.

Engine modules under `engine/modules/` and `engine/core/` (other than
the loader and `paths.js`) take profile data as arguments and never
read from `profiles/` directly. This single-read-point rule is
enforced at code-review time — a grep for `profiles/` in
`engine/modules/` or `engine/core/` (excluding `profile_loader.js` and
`paths.js`) should match nothing.
