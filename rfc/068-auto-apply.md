# RFC 068 — Автоподача заявок

- **Status:** Accepted (2026-10-20 — кандидат утвердил образ и план, ответил на открытые вопросы)
- **Tier:** L (новая команда, новая зависимость, новый столбец TSV, смена продуктового принципа)
- **Меняет принцип:** `docs/product/vision.md:56`, `:99` и `README.md:124` — «No auto-apply». После принятия RFC — правятся в том же PR, что этап 1.

## Problem

Пайплайн доводит вакансию до статуса `To Apply` с готовым резюме и cover letter, а дальше нужен человек: открыть форму, заполнить, ответить на вопросы, нажать Submit. Кандидат на этом шаге не масштабируется — в `To Apply` сейчас 159 строк, в `Inbox` 513. Внешний бот, который закрывал этот шаг, стоил в 2,5 раза дороже подписки и дал результат только первый месяц.

Цель — стабильный поток приглашений на интервью без затрат времени кандидата.

## Goals

1. Ночью бот сам подаёт заявки на Greenhouse / Lever / Ashby: заполняет форму, прикладывает файлы, отвечает на вопросы, нажимает Submit, проверяет подтверждение.
2. На вопрос, которого нет в банке, бот пишет ответ сам из материалов кандидата и сохраняет его в банк.
3. Подаются только вакансии, проходящие правила кандидата: Strong/Medium; Калифорния — любой формат, другие штаты — только удалёнка; ≤ 3 заявки в компанию за 30 дней; никогда повторно.
4. Реестр откликов — локальная страница в браузере, включая подачи старого бота (импорт из Zoho).
5. Еженедельный отчёт для разбора стратегии.
6. **Целевой объём — 100 заявок за ночь.** Всё, что можно, делается агентами параллельно (§11).

## Non-goals

- LinkedIn Easy Apply (ToS, риск бана).
- Решение капчи, заведение аккаунтов, ввод паролей ботом.
- Workday / iCIMS / SmartRecruiters — этап 2, отдельный RFC.
- Письма нанимающим (BL-176), Telegram-источник (BL-204) — отдельные задачи после этапа 1.

## Proposal

### 1. Команда `apply` (новая)

`engine/commands/apply.js`, три фазы по образцу `prepare` / `check`: детерминированный CLI → LLM-шаг в скилле → детерминированный CLI.

```
node engine/cli.js apply --profile jared --phase pre    [--limit N]
node engine/cli.js apply --profile jared --phase submit --answers-file <f> [--dry-run]
```

**`--phase pre`** — для очереди кандидатов на подачу:
- очередь = строки `To Apply` (включая только что созданные `prepare commit`), отсортированные по дате публикации, свежие первыми;
- гейты: `fit_score ∈ {Strong, Medium}`; гео-правило (§3); company cap (переиспользуем `buildActiveCounts` и правило `evaluate_job.js:202`); не подано ранее (`applied_date` пусто и `status ∉ {Applied, Interview, Offer, Rejected, No Response}`); URL жив;
- ссылки-агрегаторы (Adzuna, рассылки) резолвятся по редиректу до настоящей формы; ATS определяется по хосту; неподдержанный ATS → `apply_state=manual`, причина `unsupported_ats:<host>`;
- открывает форму в Playwright, снимает схему полей (стандартные, файлы, кастомные вопросы с типом и вариантами);
- кастомные вопросы сопоставляет со стандартными ответами профиля (§4) и с банком (`qa_notion.searchAnswers`);
- пишет `profiles/<id>/.apply-state/apply_context.json`: по каждой вакансии — схема формы, найденные ответы, вопросы без ответа.

**LLM-шаг (скилл `job-pipeline`, новый режим `apply`)** — читает `apply_context.json`, на каждый вопрос без ответа пишет ответ из `master_profile.md`, `fit_profile.md`, сторибанка (`interview-coach-state/coaching_state.md`, раздел Storybank) и `profile.json.memory`, со стилем `profile.answer.*`. Каждый ответ проходит независимую проверку на правду (агент по образцу `konspekt-truth-review`): каждое утверждение — из источника, нет «co-founder», код — как AI-native builder, без выдуманных цифр. Не прошёл после одной переписки → вакансия `manual`, причина `no_honest_answer`. Прошедшие ответы пушатся в банк существующим `answer --phase push` и пишутся в `answers-<ts>.json`.

**`--phase submit`** — по каждой вакансии:
- заполняет форму: identity (§5), резюме-PDF (тейлоренный путь из `resume_ver`, иначе архетип через новый резолвер ключ→файл `resumes/CV_Jared_Moore_<Archetype>.pdf`), cover letter PDF, ответы;
- проверка перед отправкой: все обязательные поля заполнены, файлы приложены, ни одно поле не пустое из-за промаха селектора;
- капча / вход в аккаунт / непредвиденный экран → не отправляет, `manual` с причиной и скриншотом;
- Submit → ждёт подтверждение (текст или смена URL по правилам адаптера); нет подтверждения → `failed`, повторной отправки нет;
- успех → `status=Applied`, `applied_date`, `applied_by=bot`, скриншот подтверждения в `profiles/<id>/.apply-state/shots/`; Notion обновляется существующим путём смены статуса.

`--dry-run` проходит всё до Submit и останавливается — для приёмки адаптеров.

### 2. Адаптеры форм

`engine/modules/apply/<ats>.js` — `greenhouse.js`, `lever.js`, `ashby.js`. Контракт: `detect(url)`, `open(page, url)`, `readSchema(page) → fields[]`, `fill(page, values)`, `submit(page) → {ok, evidence}`. Селекторы живут только в адаптере. Тесты — на сохранённых синтетических HTML-фикстурах форм, без сети.

Зависимость: `playwright-core`; браузер — Chromium из `~/Library/Caches/ms-playwright` (уже скачан на машине) или `npx playwright install chromium`. Постоянный профиль браузера `~/Library/Application Support/ai-job-searcher/browser/<profile>/` — для этапа 2 (вход кандидатом), на этапе 1 только хранит cookies.

Решение RFC 045 против puppeteer касалось PDF и не меняется: PDF остаётся на `chrome --print-to-pdf`, Playwright живёт только в `apply`.

### 3. Гео-правило подачи

Новый режим в `geo_enforcer.js`: `home_state_or_remote` с `home_state: "CA"`.
- локация в CA (любой формат) → проходит;
- вне CA → только удалённая: `workplaceType` / `isRemote` из ATS, иначе маркер `Remote` в локации или заголовке;
- «San Francisco, CA or Remote» → проходит; «New York (Hybrid)» → нет; неоднозначно → нет.

Работает и в `prepare` (чтобы не тратить тейлор на то, что не подастся), и в `apply --phase pre` (страховка для старых `To Apply`). Профиль: `profile.json.geo = { mode: "home_state_or_remote", home_state: "CA" }`.

### 4. Стандартные ответы профиля

Новый файл `profiles/<id>/apply_defaults.json` — типовые вопросы без генерации:
- work authorization — да; sponsorship — нет; relocation — нет;
- EEO (gender, race, veteran, disability) — «Decline to self-identify» или ближайший вариант;
- how did you hear — источник вакансии;
- desired salary — правило (§4a);
- LinkedIn / сайт — из identity.

Сопоставление — нормализованный текст + синонимы, без LLM. Шаблон с синтетикой — в `profiles/_example/`.

#### 4a. Зарплата

- Опубликован диапазон и его верх < $120,000 → вакансия не подаётся (`skip_reason=salary_below_floor`), фильтр работает уже в `prepare`.
- Опубликован диапазон → в поле пишется верх диапазона (не ниже $120,000); если форма просит диапазон — опубликованный диапазон, с нижней границей не ниже $120,000.
- Диапазон не опубликован → $180,000.
- Значения пола и дефолта — в `apply_defaults.json` (`salary.floor`, `salary.default`).

### 5. Email для заявок

`profile.json.identity.email` → `jrdmrpm@gmail.com`: тейлоренные резюме, перегенерация архетипов `CV_Jared_Moore_*.pdf`, формы.

Проверка почты читает **оба** ящика: старый (`JARED_GMAIL_*`) — ответы по уже поданным заявкам, новый (`JARED_APPLY_GMAIL_USER` / `JARED_APPLY_GMAIL_APP_PASSWORD`) — по заявкам бота. Значения вносит кандидат в `.env`; на fly — тем же `scripts/set_fly_secrets_jared.sh`.

### 6. TSV v8

Новые столбцы (append-only, паттерн v7):
- `applied_by` — `bot` | `manual` | `legacy_bot`;
- `apply_state` — `""` | `manual` | `failed` | `submitted`;
- `apply_note` — причина `manual`/`failed` или путь к скриншоту.

Запись только через `applications_tsv.js`.

### 7. Импорт из Zoho

`scripts/import_zoho_applications.js --profile jared [--apply]` (по умолчанию dry-run):
- IMAP `imap.zoho.com` по `JARED_ZOHO_USER` / `JARED_ZOHO_APP_PASSWORD`, либо экспорт ящика (`--mbox <path>`);
- письма-подтверждения ATS (классификатор `ack` из tracking) → компания, роль, дата;
- совпадение со строкой TSV (компания + нормализованный title) → `status=Applied`, `applied_by=legacy_bot`, `applied_date`; нет совпадения → новая строка `source=legacy_bot`, `status=Applied`;
- отказы и приглашения из того же ящика → соответствующий статус тем же классификатором.

Эти строки сразу участвуют в «не подавать повторно» и в company cap.

### 8. Реестр — локальная страница

`node engine/cli.js board --profile jared` — по образцу доски piggy-bank: маленький сервер на Node `http` на 127.0.0.1, токен в URL, проверка Host/Origin, lock-файл с портом, самовыключение через 30 минут простоя. Статика в `engine/ui/board/`, данные — JSON API, перечитывающий TSV на каждый запрос; чужой текст — через `textContent`.

Вкладки:
- **Отклики** — таблица: компания, роль, дата подачи, кто подал, статус, оценка, ссылка; поиск, фильтры, сортировка;
- **Доделать руками** — `apply_state=manual` с причиной и ссылкой на форму;
- **Неделя** — цифры последнего еженедельного отчёта.

Страница только читает. Ярлык на рабочем столе.

### 9. Ночной запуск

Claude desktop scheduled task `job-apply-jared` (как существующий `job-scan-jared`), каждую ночь: `scan` → `prepare` (pre → skill → commit) → `apply` (pre → skill → submit) циклом, пока есть очередь, не наступило 06:00 PT и не исчерпан бюджет использования (как в night-run через `get_usage`). Условие: Mac не спит и приложение Claude открыто — проверяется на старте, пропуск пишется в лог.

`job-scan-jared` поглощается новой задачей — одна ночная задача вместо двух конкурирующих.

### 10. Еженедельный отчёт

Scheduled task по воскресеньям: из TSV — подано / ответы / приглашения / отказы за неделю и накопительно, в разрезе оценки, архетипа, источника, ATS, гео, возраста вакансии на момент подачи; топ причин `manual` / `failed`. Страница в `~/ClaudeData/ai-job-searcher/reports/` и сводка на вкладке «Неделя». Разбор — в сессии с кандидатом, решения — задачами в бэклог.

### 11. Пропускная способность: 100 заявок за ночь

Узкие места и как их снимаем:
- **LLM-шаги параллельно.** Оценка — существующий `pipeline-fit-evaluator` (по агенту на вакансию, RFC 044); тейлор — `resume-tailor-mirror`; ответы на новые вопросы и проверка на правду — по агенту на вакансию. Оркестратор ночной задачи раздаёт пачки по 10–20.
- **Браузер параллельно.** `apply --phase submit --concurrency N` — N контекстов Playwright (по умолчанию 4), каждый ведёт свою вакансию; per-host ограничение 1 одновременная форма на один ATS-тенант.
- **Кэш.** Ответы из банка и `apply_defaults` закрывают большинство вопросов без LLM; тейлор только для Strong (Medium — архетип), как сейчас.
- **Поток вакансий.** 100 за ночь требует ~100 подходящих Strong/Medium в день после гео- и зарплатных фильтров. Если источников не хватает — это увидит еженедельный отчёт («подано / доступно»), расширение источников — отдельные задачи.
- **Бюджет подписки.** Ночная задача читает `get_usage` между пачками и останавливается, не доходя до лимита.

### 12. Старые `To Apply`

Разово при запуске: все строки `To Apply` без `applied_date` → `Archived`, `skip_reason=stale_pre_autoapply` (TSV + Notion через существующий путь смены статуса). Бот подаёт только на вакансии, найденные после запуска.

## Безопасность и качество (подача без человека)

- Никогда два раза одну вакансию: проверка `applied_date` непосредственно перед Submit + запись статуса сразу после подтверждения; неподтверждённая отправка автоматически не повторяется.
- Никаких выдуманных фактов: проверка ответов на правду до отправки (§1).
- Бот не вводит пароли и не заводит аккаунты; встретил вход или капчу — останавливается.
- Секреты только из `.env` через `profile_loader.loadSecrets`.
- PII-guard: фикстуры форм синтетические.

## Acceptance criteria

- За ночь бот подаёт заявки на Greenhouse/Lever/Ashby без участия кандидата; каждая — с подтверждением и `Applied` в TSV/Notion.
- Ни одной повторной подачи, ни одной вне гео-правила или сверх company cap (тесты + сверка по реестру после первой недели).
- Новые вопросы получают ответ из материалов кандидата и попадают в банк.
- Капча / вход / неподдержанный ATS → вкладка «Доделать руками» с причиной.
- Подачи старого бота из Zoho видны в реестре и блокируют повтор.
- Реестр открывается ярлыком; еженедельный отчёт появляется по воскресеньям.

## Decisions (2026-10-20, кандидат)

1. Зарплата: пол $120k; при опубликованном диапазоне — от него; без диапазона — $180k (§4a).
2. Старые `To Apply` — не подавать, в архив (§12).
3. Цель — 100 заявок за ночь, максимум работы агентам (§11).
