Five P0/P1 fixes from the 2026-05-18 pipeline audit (`private/audit-internal/2026-05-18-pipeline-audit.md`). **BL-79**: `title_blocklist` semantics unified between `scan` (`engine/core/filter.js` `matchBlocklists`) and `prepare-pre` (`applyPrepareFilter`) via new shared helper `findTitleBlocklistHit(title, patterns)`. Closes the class of bug where blocklist `"rn"` would false-match `"PRN Coordinator"` in `applyPrepareFilter` but not in `matchBlocklists`. **BL-81**: `US_MARKERS` / `US_STATE_CODES` / `US_STATE_NAMES` / `hasUsMarker` consolidated in `engine/core/geo_enforcer.js` as the single source of truth; `engine/core/filter.js` now imports them. Sets unioned — `"u.s.a"` and full state names (e.g. `"California"` alone) now classify as US in `filter.js` context too, eliminating scan-vs-prepare divergence. BL-24 "US in ANY `locations[]` element wins" preserved + tested cross-fixture. **BL-86**: `engine/modules/discovery/remoteok.js` `buildTitleFilter` now reads the flat `[{pattern, reason}]` shape that `profile_loader.normalizeFilterRules` actually emits — previously read `filterRules.title_requirelist.patterns` which was always `undefined`, silently falling back to `DEFAULT_PM_RE`. For PM profiles (jared) the fallback accidentally matched intent; for non-PM profiles (lilia) it worked inverted, rejecting everything except PM roles. Legacy `{patterns: [...]}` shape preserved for back-compat. **BL-87**: `engine/modules/discovery/adzuna.js` now derives keywords from `filterRules.role_targets.tracks[].patterns` when `discovery.keyword_search.keywords` is absent or empty (RFC 033 "role_targets as single source of truth" applied to adzuna). New helpers `stripAnchors` / `expandSimpleAlternation` / `patternToKeywords` / `deriveKeywordsFromRoleTargets`: strip `\b` / `^` / `$`, expand simple `(a|b|c)` groups, dedupe case-insensitively, skip patterns too regex-y to convert without throwing. RFC 033 §2.5 added. **BL-100**: `engine/core/email_filters.js` `isLevelBlocked` / `isLocationBlocked` now use word-boundary semantics — `isLevelBlocked` calls the shared `findTitleBlocklistHit` from filter.js; `isLocationBlocked` inlines a `makeBoundaryRegex` mirror (filter.js does not export it and the BL forbade touching filter.js). Closes the same class of bug as BL-79 for emails. `npm test`: 1407/1407 across all five.

- **`companies.js`: allow empty `ats_slug` for `source=manual`** (BL-67, 2026-05-15). `parseLine` in `engine/core/companies.js` required `name / ats_source / ats_slug` for every row. Pre-existing `data/companies.tsv` rows of the form `Virto Commerce<TAB>manual<TAB><TAB>...` (metadata-only entries used for referral tracking — BL-55) tripped the loader and broke `scan`. Validation is now source-aware: `name` and `ats_source` are still required for every row, but `ats_slug` is only required when the source is adapter-driven (`greenhouse`, `lever`, `ashby`, etc.). `source=manual` rows pass through with empty slug. Three new tests cover the cases: missing `ats_source` still throws, missing slug on an adapter-driven source still throws, and `source=manual` with empty slug is accepted.
- **`scan`: remove `company_cap` at scan stage (apply-time only)** (BL-67, 2026-05-15). `engine/commands/scan.js` no longer evaluates `filter_rules.company_cap` when filtering discovered jobs. The cap was originally meant as an apply-time safeguard against over-applying to one employer; firing it at the discovery stage was hiding 50-500-role frontier AI labs (OpenAI / Anthropic / Scale) at `max_active=3` and blocking the Inbox from ever surfacing FDE / Solutions / AI PM signal for downstream `prepare`. The cap is still enforced inside `prepare --phase pre` step 4 when promoting `Inbox → To Apply`, where its semantics actually match the intent (don't pile 4 active applications onto the same employer). Test `scan filter: company_cap counts active rows from existing apps` rewritten as `scan filter: company_cap does NOT fire at scan stage (apply-time only)`. `docs/reference/cli.md` updated to drop the misleading "applies `filter_rules` + `company_cap`" phrasing under `scan`. 1208/1208 tests pass.

- **`validate --dedup`: collapse legacy-prefix collisions in `applications.tsv`** (BL-9 Step 6, 2026-05-05). Standalone subtask of `validate` (skips company-cap / URL-liveness / retro-sweep). Detects rows whose canonical key (source + jobId after recursively stripping ATS prefixes) matches another row. Catches `lever:abc` ↔ `lever:lever:abc` pairs produced by the discovery key-prefix migration. Winner per group: row with `notion_page_id` → higher status (`Offer > Interview > Applied > To Apply > Inbox > No Response > Rejected > Closed > Archived`) → newer `updatedAt` → shorter key. Loser fields (`fit_score`, `cl_path`, `location`, `salary_min`, `salary_max`, `resume_ver`, `cl_key`, `fit_rationale`, `fit_evaluated_at`, `skip_reason`) are lifted into the winner only when the winner's field is empty — accumulated state isn't lost. Groups whose rows disagree on company or url path (after stripping query+fragment) are flagged as **suspicious**, surfaced in the report, and never auto-collapsed (manual review). Default: dry-run report (`found: N duplicate group(s)`, `by reason`, examples, `rerun with --apply`). With `--apply`: rewrites TSV after copying the original to `applications.tsv.pre-dedup-<timestamp>`. New module `engine/core/tsv_dedup.js` (pure: `planDedup`, `canonicalKey`, `pickWinner`, `mergeLosersInto`, `rowsAreSuspicious`, `stripAllPrefixes`). New CLI flag `--dedup` (validate only). Tests: 21 unit (canonical-key normalization, priority resolution, multi-collision, suspicious detection, ordering preservation, mergeable fields) + 7 integration (dry-run report, --apply with backup, suspicious not collapsed, parse error path, skips other validate steps, backup filename format). `npm test`: 988/988.

### Changed

- **`prepare.js`: `enforceGeo` called once per entry instead of twice** (BL-102, 2026-05-18). Audit §2 caught `applyPrepareFilter` (lines 127-232) calling `enforceGeo` for filter decisions and `buildBatchEntry` (lines 333-339) calling it AGAIN to annotate `geo_decision` in the batch entry — by construction the entry already passed `applyPrepareFilter`, so the second call was pure duplicate work. Fix: `applyPrepareFilter` attaches the `enforceGeo` result as `_geoResult` on a shallow clone of each passing app; the cache flows through `core/url_check.js` via `{ ...row, ... }` spread and reaches `urlRes` in `buildBatchEntry`, which now reads `urlRes._geoResult` directly. Three call sites of `buildBatchEntry` all feed off `aliveResults` from `fillUpAliveBatch`, so the cache propagates uniformly. Behavior change: zero (pinned `prepare.test.js` `entry.geo_decision === "allowed"` tests pass). Edge case: when `mode === "unrestricted"`, `applyPrepareFilter` previously skipped enforceGeo entirely; now it still calls once (always `{ok:true, matchedBy:"unrestricted"}`), and `buildBatchEntry` reads from cache — same observable output as before. Net: one fewer `enforceGeo` invocation per batch entry.

- **`prepare --phase pre` auto-collapses TSV duplicates before any other work** (BL-13, 2026-05-06). Code-first replacement for the manual `validate --dedup --apply` workflow. At the start of `runPre` (fresh mode) the engine plans a dedup pass over `applications.tsv`; if there are any non-suspicious duplicate groups it backs the TSV up to `applications.tsv.pre-dedup-<ISO>`, applies the collapse, saves, and prints an explicit acknowledgement on stdout: `dedup: found N duplicate group(s) in TSV — auto-collapsed, kept M row(s), removed K row(s) (backup: <basename>)`. When the TSV is already clean the line is suppressed entirely so quiet runs stay quiet. Suspicious groups (rows with the same canonical key but different company / different URL path) are NEVER auto-collapsed — they're surfaced as a stderr warning so the user can review via `validate --dedup`. Dry-run reports `would auto-collapse N duplicate group(s)` without writing. `validate` (without `--dedup`) gains a read-only `tsv_dedup` step that prints the duplicate count plus a hint that the next `prepare --phase pre` will collapse them; the existing `validate --dedup --apply` path is unchanged for backwards compatibility. New `runAutoDedup(apps, applicationsPath, ctx, deps)` helper exported from `engine/commands/prepare.js`. New deps slot: `copyFileSync` (default `fs.copyFileSync`). 7 new tests across `prepare.test.js` (silent on clean TSV, collapse with backup + explicit message, suspicious untouched, dry-run plans, missing TSV skips backup, end-to-end auto-dedup before filter, dry-run no write) and 4 new in `validate.test.js` (detect on stdout, suspicious on stderr, clean ok, --dedup --apply backwards-compat). The user no longer has to invoke any dedup command — running `/job-pipeline prepare` is enough.
- **`makeKey(source, jobId)` is idempotent against doubled ATS prefixes** (BL-12, 2026-05-06). `engine/core/applications_tsv.js` now strips any leading `gh:` / `ashby:` / `lever:` / `workday:` / `smart:` / `sr:` prefix from `jobId` before joining, so `makeKey("lever", "abc")`, `makeKey("lever", "lever:abc")`, and `makeKey("lever", "lever:lever:abc")` all return `lever:abc`. Closes the root cause of the legacy-prefix collision that BL-9 step 6 (`validate --dedup`) had to clean up post-hoc — the duplicate row never lands in TSV in the first place. Case of the surviving id is preserved (workday IDs like `REQ-9991` round-trip unchanged) — only the recognized ATS prefix is consumed. 4 new tests cover idempotency, supported prefix list, case preservation for non-prefixed IDs, and `appendNew()` deduping when a discovery adapter returns the same id with and without prefix.

- **`applications.tsv` schema v3 → v4** (BL-9, 2026-05-05). Added four columns to persist Claude's fit verdict per row: `fit_score` (`Strong` / `Medium` / `Weak`), `fit_rationale`, `fit_evaluated_at`, `skip_reason` (SKILL-level only: `weak_fit` / `duplicate`). Subsequent `prepare` runs will skip already-evaluated rows instead of re-paying the SKILL cost. Auto-upgrade on read from v1 / v2 / v3 with empty fit columns; writes always emit v4. Engine-level skips (company cap, blocklists, geo) continue to be recomputed each run and are not persisted. See [docs/reference/tsv-schema.md](docs/reference/tsv-schema.md).
- **`prepare --phase pre` skips already-evaluated rows** (BL-9, 2026-05-05). New filter step runs before `applyPrepareFilter`: rows with `fit_score=Weak` or `skip_reason ∈ {weak_fit, duplicate}` no longer reach URL-check / JD-fetch / SKILL judgement. They appear in `prepare_context.json` `skipped[]` with reasons `already_evaluated_weak` / `already_evaluated_duplicate` and a new `stats.alreadyEvaluated` counter. Dramatically reduces token cost on repeat runs once fit verdicts have been persisted.
- **`prepare --phase commit` persists fit verdict for every decision** (BL-9, 2026-05-05). SKILL results JSON now carries `fitScore` / `fitRationale` / `skipReason` on every result (`to_apply` / `skip` / `archive`). Engine writes them to TSV columns `fit_score` / `fit_rationale` / `skip_reason` and stamps `fit_evaluated_at = now` whenever a `fit_score` is present. Validators reject invalid values (`fitScore` must be Strong/Medium/Weak; `skipReason` must be weak_fit/duplicate) with a stderr warning instead of corrupting the column. Stdout summary surfaces `fitWritten` count. Downgraded-to-skip rows (invalid resumeVer) still capture the verdict so they are not re-evaluated next run.
- **`prepare --phase pre --mode topup`: two-pass batch refill** (BL-9, 2026-05-05). `--phase pre` now runs in two modes. `--mode fresh` (default) preserves the original behavior **and** persists the unconsumed (still-eligible) tail of the filter pipeline as `deferredQueue[]` (an array of TSV keys) on `prepare_context.json`. `--mode topup` reads the existing context, pulls the next `--need K` keys from the queue, re-validates them against the current TSV (drops keys that have moved out of Inbox, gained `fit_score=Weak`, or now fail `applyPrepareFilter` after rule changes), URL-checks + JD-fetches the residue, and **appends** new entries to `batch[]`. Counters (`urlChecked` / `urlAlive` / `urlDead` / `alreadyEvaluated` / `topupRuns`) accumulate across runs; `skipReasons` is recomputed from the merged `skipped[]`. Use this after a SKILL run where Strong + Medium fell below `batchSize` so the next operator turn picks up where the last one left off without a fresh scan. New CLI flags: `--mode <fresh|topup>` (default `fresh`), `--need <k>` (default = `batchSize - len(currentBatch)`).
- **`prepare` autonomous loop with priority Strong→Medium→Weak** (BL-9 Step 5, 2026-05-05). The user invokes `/job-pipeline prepare` once; the SKILL orchestrates a multi-iteration loop until 30 jobs land in Notion or the Inbox is exhausted. Engine: new `--mode weak-fallback --need K` reads `deferredQueue` plus already-Weak fresh-Inbox rows in TSV; entries get `wasAlreadyWeak: true` + `priorFitScore` + `priorFitRationale` so the SKILL reuses the saved verdict instead of re-judging. `filterAlreadyEvaluated({mode:"weak-fallback"})` keeps Weak rows; `duplicate`-flagged rows are still always dropped. Engine: new `stats.inboxExhausted: bool` written by all three modes (fresh / topup / weak-fallback) — true when no more fresh rows exist in TSV outside the current batch (excluding duplicates; in non-weak-fallback modes, already-Weak rows still count as not-exhausted). SKILL.md `prepare` section rewritten as autonomous loop spec: max 3 iterations of `topup` chasing Strong (loop stops only on Strong ≥ 30 / iter ≥ 3 / `inboxExhausted` — Mediums never satisfy the target since selection is sequential Strong→Medium→Weak), then `weak-fallback` to fill the rest if Strong+Medium still short, then push top-30 to Notion in priority order. Step 9 (Notion push) and Step 10 (results.json) now run ONCE on the final top-N list, not per iteration. Step 5 reframed as bucket-assignment (verdicts.strong / medium / weak) — final to_apply / skip is decided in the loop's selection phase, not per job.
