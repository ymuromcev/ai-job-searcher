### Changed

- **`applications.tsv` schema v3 → v4** (BL-9, 2026-05-05). Added four columns to persist Claude's fit verdict per row: `fit_score` (`Strong` / `Medium` / `Weak`), `fit_rationale`, `fit_evaluated_at`, `skip_reason` (SKILL-level only: `weak_fit` / `duplicate`). Subsequent `prepare` runs will skip already-evaluated rows instead of re-paying the SKILL cost. Auto-upgrade on read from v1 / v2 / v3 with empty fit columns; writes always emit v4. Engine-level skips (company cap, blocklists, geo) continue to be recomputed each run and are not persisted. See [docs/reference/tsv-schema.md](docs/reference/tsv-schema.md).
- **`prepare --phase pre` skips already-evaluated rows** (BL-9, 2026-05-05). New filter step runs before `applyPrepareFilter`: rows with `fit_score=Weak` or `skip_reason ∈ {weak_fit, duplicate}` no longer reach URL-check / JD-fetch / SKILL judgement. They appear in `prepare_context.json` `skipped[]` with reasons `already_evaluated_weak` / `already_evaluated_duplicate` and a new `stats.alreadyEvaluated` counter. Dramatically reduces token cost on repeat runs once fit verdicts have been persisted.
- **`prepare --phase commit` persists fit verdict for every decision** (BL-9, 2026-05-05). SKILL results JSON now carries `fitScore` / `fitRationale` / `skipReason` on every result (`to_apply` / `skip` / `archive`). Engine writes them to TSV columns `fit_score` / `fit_rationale` / `skip_reason` and stamps `fit_evaluated_at = now` whenever a `fit_score` is present. Validators reject invalid values (`fitScore` must be Strong/Medium/Weak; `skipReason` must be weak_fit/duplicate) with a stderr warning instead of corrupting the column. Stdout summary surfaces `fitWritten` count. Downgraded-to-skip rows (invalid resumeVer) still capture the verdict so they are not re-evaluated next run.
- **`prepare --phase pre --mode topup`: two-pass batch refill** (BL-9, 2026-05-05). `--phase pre` now runs in two modes. `--mode fresh` (default) preserves the original behavior **and** persists the unconsumed (still-eligible) tail of the filter pipeline as `deferredQueue[]` (an array of TSV keys) on `prepare_context.json`. `--mode topup` reads the existing context, pulls the next `--need K` keys from the queue, re-validates them against the current TSV (drops keys that have moved out of Inbox, gained `fit_score=Weak`, or now fail `applyPrepareFilter` after rule changes), URL-checks + JD-fetches the residue, and **appends** new entries to `batch[]`. Counters (`urlChecked` / `urlAlive` / `urlDead` / `alreadyEvaluated` / `topupRuns`) accumulate across runs; `skipReasons` is recomputed from the merged `skipped[]`. Use this after a SKILL run where Strong + Medium fell below `batchSize` so the next operator turn picks up where the last one left off without a fresh scan. New CLI flags: `--mode <fresh|topup>` (default `fresh`), `--need <k>` (default = `batchSize - len(currentBatch)`).
- **`prepare` autonomous loop with priority Strong→Medium→Weak** (BL-9 Step 5, 2026-05-05). The user invokes `/job-pipeline prepare` once; the SKILL orchestrates a multi-iteration loop until 30 jobs land in Notion or the Inbox is exhausted. Engine: new `--mode weak-fallback --need K` reads `deferredQueue` plus already-Weak fresh-Inbox rows in TSV; entries get `wasAlreadyWeak: true` + `priorFitScore` + `priorFitRationale` so the SKILL reuses the saved verdict instead of re-judging. `filterAlreadyEvaluated({mode:"weak-fallback"})` keeps Weak rows; `duplicate`-flagged rows are still always dropped. Engine: new `stats.inboxExhausted: bool` written by all three modes (fresh / topup / weak-fallback) — true when no more fresh rows exist in TSV outside the current batch (excluding duplicates; in non-weak-fallback modes, already-Weak rows still count as not-exhausted). SKILL.md `prepare` section rewritten as autonomous loop spec: max 3 iterations of `topup` chasing Strong (loop stops only on Strong ≥ 30 / iter ≥ 3 / `inboxExhausted` — Mediums never satisfy the target since selection is sequential Strong→Medium→Weak), then `weak-fallback` to fill the rest if Strong+Medium still short, then push top-30 to Notion in priority order. Step 9 (Notion push) and Step 10 (results.json) now run ONCE on the final top-N list, not per iteration. Step 5 reframed as bucket-assignment (verdicts.strong / medium / weak) — final to_apply / skip is decided in the loop's selection phase, not per job. Tests: 20 new for weak-fallback + inboxExhausted + isFreshInboxApp helper (`npm test`: 960/960).
