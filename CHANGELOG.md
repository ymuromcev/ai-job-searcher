### Changed

- **`company_cap` is now a rolling 30-day window instead of an all-time count (BL-136, 2026-05-27)**. Before today, `engine/commands/prepare.js#buildActiveCounts` summed every `To Apply` / `Applied` / `Interview` / `Offer` row a profile had ever recorded for a company, so a candidate who pitched Stripe three times a year ago was permanently locked out of every fresh Stripe role. The cap now counts only rows whose `updatedAt` is within the last `window_days` days (default 30); older touchpoints age out and the company becomes "live" again automatically. Window length is configurable per profile via `filter_rules.company_cap.window_days`. The set of counted statuses widened in the same change to `To Apply / Applied / Interview / Offer / Rejected / Closed / No Response` (`Inbox` and `Archived` still don't count) — within the window, a recent Rejected still counts as a touchpoint, so the cap protects against re-pitching a company that just said no. **Backward compatibility**: if a profile's `filter_rules.json` is missing the `window_days` field, `buildActiveCounts` falls back to the legacy all-time count so existing profiles keep working on first run after upgrade. This fallback will be removed in the next release — add `"window_days": 30` to `company_cap` in your `filter_rules.json` to opt in explicitly. `profiles/_example/filter_rules.example.json` already advertises the field. 9 new unit tests in `engine/commands/prepare.test.js` cover (a) 0/1/3 in-window apps → cap=3/2/0, (b) the canonical regression case (5 apps all-time but 0 in last 30d → cap=3), (c) missing `window_days` fallback, (d) rows with unparseable `updatedAt` are dropped under windowed mode, (e) per-company `overrides` still apply on top, (f) `resolveCapWindowDays` parser handles junk values. 1849/1849 tests pass.

### Added

- **`prepare`: orphan evaluated rows reach Notion via `alreadyEvaluated[]` carry-over (BL-135 / [RFC 049](rfc/049-orphan-evaluated-rows.md), 2026-05-27)**. RFC 034 (BL-80) fixed the forward path so every evaluated row — including `Weak` — lands in Notion at commit, but it never handled the **retro pool**: rows judged before BL-80 landed have `fit_score=Weak` + empty `notion_page_id` and were silently dropped by `filterAlreadyEvaluated` under reason `already_evaluated_weak`. On 2026-05-27 in `profiles/jared` this was 86 such rows (~85 from the pre-BL-80 era 2026-05-11..2026-05-17, plus 1 outlier from 2026-05-19). They sat in TSV forever — never re-evaluated, never pushed to Notion, never visible to the operator. `engine/commands/prepare.js#filterAlreadyEvaluated` now returns three buckets (`passed`, `skipped`, `alreadyEvaluated`); `Weak` rows route to `alreadyEvaluated[]` when `notion_page_id` is empty (orphan), and to `skipped[]` when set (already in Notion, RFC 034 forward path). Pre-phase emits a new `alreadyEvaluated[]` top-level field on `prepare_context.json` carrying `{key, companyName, title, url, source, jobId, fitScore, fitRationale, clKey, clPath, resumeVer}` per orphan row, plus a new `stats.alreadyEvaluatedCarryOver` counter. The SKILL never reads this field — engine-side aggregator. Commit-phase loads `alreadyEvaluated[]` via the new `loadAlreadyEvaluatedCarryOver` helper, synthesizes results-style entries (dedup-by-key against SKILL `results[]` so a fresh re-eval wins), and prepends them to the dispatch loop. Carry-over rows traverse the same Notion-push pipeline as fresh evaluated rows: TSV transitions `Inbox → To Apply`, Notion page created, fit verdict preserved. CL handling per RFC 034 §5 option A — `Weak` carry-over pushes without CL (operator generates on-demand if they triage to apply); `Medium`/`Strong` carry-over with empty `cl_path` warns to stderr and pushes with an empty Cover Letter field (none observed in jared). Topup mirrors the contract: re-runs `filterAlreadyEvaluated` on the live queue and appends to `prev.alreadyEvaluated` (deduped by key). **Operator impact**: the first prepare run after merge will push ~86 new Notion pages on jared in a single commit — flagged in RFC §8 and surfaced via stdout (`already-evaluated: carry-over N (orphan Weak from prior runs — will push to Notion in commit)`) so it doesn't look like a runaway loop. 7 new unit tests cover (a) orphan routing, (b) legacy `skip_reason=weak_fit` alias, (c) Archived precedence, (d) pre-phase context shape, (e) commit happy path, (f) commit Notion failure → revert to Inbox, (g) commit dedup when SKILL has the same key. Three existing `filterAlreadyEvaluated` tests updated to set `notion_page_id` (those test the "already in Notion" branch of the new split contract). 1841/1841 tests pass.

### Added

- **Ashby JD fetcher closes BL-95/96 gap (BL-129, 2026-05-25)**. `engine/core/jd_cache.js` gains `buildAshbyApiUrl` + `formatAshby` + the `ashby` dispatcher case, and `ashby` moves from `JD_UNSUPPORTED` to `SUPPORTED`. The fetcher hits the public per-board endpoint (`https://api.ashbyhq.com/posting-api/job-board/{org}?includeCompensation=true`, no auth) — the per-job route is 401-gated, so we fetch the board and locate the requested posting by UUID. SSRF guards: org slug matches `^[a-z0-9-]{1,64}$`, jobId is canonical lowercase UUID v4, HTTPS-only, URL rebuilt from validated `job.slug`/`job.jobId` (a tampered `url` field cannot redirect the fetch). - **`prepare --phase pre` auto-collapses TSV duplicates before any other work** (BL-13, 2026-05-06). Code-first replacement for the manual `validate --dedup --apply` workflow. At the start of `runPre` (fresh mode) the engine plans a dedup pass over `applications.tsv`; if there are any non-suspicious duplicate groups it backs the TSV up to `applications.tsv.pre-dedup-<ISO>`, applies the collapse, saves, and prints an explicit acknowledgement on stdout: `dedup: found N duplicate group(s) in TSV — auto-collapsed, kept M row(s), removed K row(s) (backup: <basename>)`. When the TSV is already clean the line is suppressed entirely so quiet runs stay quiet. Suspicious groups (rows with the same canonical key but different company / different URL path) are NEVER auto-collapsed — they're surfaced as a stderr warning so the user can review via `validate --dedup`. Dry-run reports `would auto-collapse N duplicate group(s)` without writing. `validate` (without `--dedup`) gains a read-only `tsv_dedup` step that prints the duplicate count plus a hint that the next `prepare --phase pre` will collapse them; the existing `validate --dedup --apply` path is unchanged for backwards compatibility. New deps slot: `copyFileSync` (default `fs.copyFileSync`). 7 new tests across `prepare.test.js` (silent on clean TSV, collapse with backup + explicit message, suspicious untouched, dry-run plans, missing TSV skips backup, end-to-end auto-dedup before filter, dry-run no write) and 4 new in `validate.test.js` (detect on stdout, suspicious on stderr, clean ok, --dedup --apply backwards-compat). The user no longer has to invoke any dedup command — running `/job-pipeline prepare` is enough.
- **`makeKey(source, jobId)` is idempotent against doubled ATS prefixes** (BL-12, 2026-05-06). `engine/core/applications_tsv.js` now strips any leading `gh:` / `ashby:` / `lever:` / `workday:` / `smart:` / `sr:` prefix from `jobId` before joining, so `makeKey("lever", "abc")`, `makeKey("lever", "lever:abc")`, and `makeKey("lever", "lever:lever:abc")` all return `lever:abc`. Case of the surviving id is preserved (workday IDs like `REQ-9991` round-trip unchanged) — only the recognized ATS prefix is consumed. 4 new tests cover idempotency, supported prefix list, case preservation for non-prefixed IDs, and `appendNew()` deduping when a discovery adapter returns the same id with and without prefix.

- **`prepare --phase pre --mode topup`: two-pass batch refill** (BL-9, 2026-05-05). `--phase pre` now runs in two modes. `--mode fresh` (default) preserves the original behavior **and** persists the unconsumed (still-eligible) tail of the filter pipeline as `deferredQueue[]` (an array of TSV keys) on `prepare_context.json`. `--mode topup` reads the existing context, pulls the next `--need K` keys from the queue, re-validates them against the current TSV (drops keys that have moved out of Inbox, gained `fit_score=Weak`, or now fail `applyPrepareFilter` after rule changes), URL-checks + JD-fetches the residue, and **appends** new entries to `batch[]`.
