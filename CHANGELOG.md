### Changed

- **TSV schema v5 — persist `locations[]` as JSON-encoded array (BREAKING)** (BL-93 / [RFC 038](rfc/038-tsv-schema-v4-locations.md), 2026-05-18). `applications.tsv` column 7 is renamed `location` (single string) → `locations` (JSON-encoded `string[]`). The schema rev fixes the multi-loc reject-by-geo bug introduced by `appendNew`'s `locations[0]` collapse: a discovery row like `["Remote (UK)", "United States"]` survived BL-24's "US-anywhere wins" rule at scan, but persisted to TSV as `"Remote (UK)"` only, and was then archived by `prepare`'s `enforceGeo` recheck (the "United States" element was already lost). `engine/core/applications_tsv.js` adds `HEADER_V5` (current) + `rowToAppV5` (`JSON.parse` decode with defensive fallback to `[cell]` on hand-edits), keeps `HEADER_V4` as read-only with a `[location] → locations` wrap, demotes the older `HEADER_V3/V2/V1` readers to also emit the new `locations: string[]` in-memory shape. Writer always emits v5; first `save()` after merge auto-upgrades any v1–v4 file end-to-end. **In-memory shape**: `app.locations: string[]` (`app.location` accessor is gone). Callers updated: `engine/commands/prepare.js` geo recheck passes the full array to `enforceGeo`; `engine/commands/validate.js` retro-sweep passes the array to `matchBlocklists`; `engine/core/tsv_dedup.js` `MERGEABLE_FIELDS` swap `location → locations` with empty-array-aware lift; `scripts/cleanup_non_us_jobs.js` reads the array; `scripts/push_prepare_results_to_notion.js` joins with `", "` for the Notion `City` field (Notion `Location` stays single-text — no `display_location` override). New one-shot `scripts/migrate_tsv_v4_to_v5.js` (dry-run by default, `--apply` to write, `--profile <id>` or scans all profiles): reads existing TSV, writes `applications.tsv.pre-v5-<YYYY-MM-DD>` backup, rewrites in v5. Idempotent — already-v5 files are a no-op. Tests: `applications_tsv.test.js` v3/v4 read-with-wrap + v5 round-trip + multi-loc + unicode/quote-safety + decodeLocations defensive fallback; new `migrate_tsv_v4_to_v5.test.js` (4 cases: v4 → v5 with backup, idempotent v5 no-op, dry-run leaves file untouched, missing-file path); new `prepare.test.js` regression `multi-loc with US in second element is NOT archived` pinning the BL-93 failure case. `docs/reference/tsv-schema.md` promoted to v5 as "current" with v4 demoted to read-only row. Adapters unaffected: every `engine/modules/discovery/*` adapter already returns `NormalizedJob.locations: string[]` (validated by `_types.js`), so no wrapping was needed at the adapter edge.

### Fixed

- **Audit 2026-05-18 pipeline follow-ups: filter & adapter bug fixes** (BL-79 / BL-81 / BL-86 / BL-87 / BL-100, 2026-05-18). Five P0/P1 fixes from the 2026-05-18 pipeline audit (`private/audit-internal/2026-05-18-pipeline-audit.md`). **BL-79**: `title_blocklist` semantics unified between `scan` (`engine/core/filter.js` `matchBlocklists`) and `prepare-pre` (`applyPrepareFilter`) via new shared helper `findTitleBlocklistHit(title, patterns)`. Closes the class of bug where blocklist `"rn"` would false-match `"PRN Coordinator"` in `applyPrepareFilter` but not in `matchBlocklists`. **BL-81**: `US_MARKERS` / `US_STATE_CODES` / `US_STATE_NAMES` / `hasUsMarker` consolidated in `engine/core/geo_enforcer.js` as the single source of truth; `engine/core/filter.js` now imports them. Sets unioned — `"u.s.a"` and full state names (e.g. `"California"` alone) now classify as US in `filter.js` context too, eliminating scan-vs-prepare divergence. BL-24 "US in ANY `locations[]` element wins" preserved + tested cross-fixture. **BL-86**: `engine/modules/discovery/remoteok.js` `buildTitleFilter` now reads the flat `[{pattern, reason}]` shape that `profile_loader.normalizeFilterRules` actually emits — previously read `filterRules.title_requirelist.patterns` which was always `undefined`, silently falling back to `DEFAULT_PM_RE`. For PM profiles (jared) the fallback accidentally matched intent; for non-PM profiles (lilia) it worked inverted, rejecting everything except PM roles. Legacy `{patterns: [...]}` shape preserved for back-compat. **BL-87**: `engine/modules/discovery/adzuna.js` now derives keywords from `filterRules.role_targets.tracks[].patterns` when `discovery.keyword_search.keywords` is absent or empty (RFC 033 "role_targets as single source of truth" applied to adzuna). New helpers `stripAnchors` / `expandSimpleAlternation` / `patternToKeywords` / `deriveKeywordsFromRoleTargets`: strip `\b` / `^` / `$`, expand simple `(a|b|c)` groups, dedupe case-insensitively, skip patterns too regex-y to convert without throwing. Explicit `keyword_search.keywords` still wins as the override path. RFC 033 §2.5 added. **BL-100**: `engine/core/email_filters.js` `isLevelBlocked` / `isLocationBlocked` now use word-boundary semantics — `isLevelBlocked` calls the shared `findTitleBlocklistHit` from filter.js; `isLocationBlocked` inlines a `makeBoundaryRegex` mirror (filter.js does not export it and the BL forbade touching filter.js). Closes the same class of bug as BL-79 for emails. `npm test`: 1407/1407 across all five.

- **`companies.js`: allow empty `ats_slug` for `source=manual`** (BL-67, 2026-05-15). `parseLine` in `engine/core/companies.js` required `name / ats_source / ats_slug` for every row. Pre-existing `data/companies.tsv` rows of the form `Virto Commerce<TAB>manual<TAB><TAB>...` (metadata-only entries used for referral tracking — BL-55) tripped the loader and broke `scan`. Validation is now source-aware: `name` and `ats_source` are still required for every row, but `ats_slug` is only required when the source is adapter-driven (`greenhouse`, `lever`, `ashby`, etc.). `source=manual` rows pass through with empty slug. Three new tests cover the cases: missing `ats_source` still throws, missing slug on an adapter-driven source still throws, and `source=manual` with empty slug is accepted.
- **`scan`: remove `company_cap` at scan stage (apply-time only)** (BL-67, 2026-05-15). `engine/commands/scan.js` no longer evaluates `filter_rules.company_cap` when filtering discovered jobs. The cap was originally meant as an apply-time safeguard against over-applying to one employer; firing it at the discovery stage was hiding 50-500-role frontier AI labs (OpenAI / Anthropic / Scale) at `max_active=3` and blocking the Inbox from ever surfacing FDE / Solutions / AI PM signal for downstream `prepare`. The cap is still enforced inside `prepare --phase pre` step 4 when promoting `Inbox → To Apply`, where its semantics actually match the intent (don't pile 4 active applications onto the same employer). Test `scan filter: company_cap counts active rows from existing apps` rewritten as `scan filter: company_cap does NOT fire at scan stage (apply-time only)`. `docs/reference/cli.md` updated to drop the misleading "applies `filter_rules` + `company_cap`" phrasing under `scan`. 1208/1208 tests pass.

### Added

- **Unified `evaluateJob` — single source of truth for filter rules (Phase 1)** (BL-92 / [RFC 040](rfc/040-unified-evaluate-job.md), 2026-05-19). New pure module `engine/core/evaluate_job.js` consolidates the three independent rule implementations that had drifted across the engine (`engine/core/filter.js` `matchBlocklists`, `engine/commands/prepare.js` `applyPrepareFilter`, `engine/core/email_filters.js` `isLevelBlocked` / `isLocationBlocked`). Single canonical signature: `evaluateJob({ job, profile, appState, context }) → { decision, skipReason, matched }`, where `context ∈ "scan" | "prepare" | "email"` selects the rule subset per the §3.1 matrix — scan/prepare apply the full set, `email` runs only `company_blocklist` + `title_blocklist`. Decision pipeline order (§3.3) is deterministic and matches today's `matchBlocklists`: company_blocklist → title_requirelist (skipped in email) → title_blocklist → company_cap (skipped in email) → location_blocklist (skipped in email) → geo (skipped in email). **Word-boundary canonical for `title_blocklist`** in every context (resolves the BL-79 / BL-100 drift class — patterns like `"rn"` no longer match `"PRN Coordinator"` regardless of call-site). **BL-24 multi-loc rule codified** for `location_blocklist`: `hasUsMarker(locations)` in any element suppresses the blocklist branch entirely. `appState.companyCounts` is read-only — `evaluateJob` reads but never mutates; callers increment on `decision === "keep"` (same contract as today's `filterJobs`). `skipReason` is always a value in `ENGINE_SKIP_REASONS` ∪ `{null}` (enum guard fuzz over 200 random tuples per context proves this). **Phase 1 shim layer** preserves every public API bit-identical for one release: `filter.js` `matchBlocklists` / `checkJob` / `filterJobs` keep their `{ kind, ... } | null` return shape via `legacyReasonForMatchBlocklists` translator + `jobFromAdapterScan` shape adapter; `prepare.js` `applyPrepareFilter` keeps its `{ passed, skipped }` shape and the BL-89 title-encoded geo composition stays inline (it composes with `enforceGeo`); `email_filters.js` `isLevelBlocked` becomes a one-liner over `evaluateJob({ context: "email" })`. `isLocationBlocked` flips to a one-release deprecation shim (`console.error` once on first call, behaviour preserved). Shape adapters live with each call-site: `jobFromAdapterScan` in `filter.js`, `jobFromTsv` in `prepare.js`, `jobFromEmail` in `email_filters.js`. The shared word-boundary primitives moved into new `engine/core/filter_helpers.js` (`makeBoundaryRegex` + `findTitleBlocklistHit`) so `evaluate_job.js` can import them without taking a runtime dependency on `filter.js`. `engine/core/skip_reasons.js` `ENGINE_SKIP_REASONS` gains `location_blocklist` (long-standing operator-visible TSV reason from the scan archive path, but never previously emitted by applyPrepareFilter; now part of the canonical enum so the enum-guard test passes for evaluateJob's prepare context). **Tests**: new `engine/core/evaluate_job.test.js` (63 cases — one row per rule × context × keep/skip, plus BL-79 / BL-24 / decision-pipeline-order fixtures and a 200-tuple enum guard fuzz per context), new `engine/core/evaluate_job.fuzz.test.js` (5 property-based tests, ~400 tuples total — scan-shim ↔ evaluateJob, prepare-shim ↔ evaluateJob, scan ↔ prepare, email title_blocklist ↔ evaluateJob, filterJobs geo ↔ evaluateJob — load-bearing: same input → same answer across call-sites). Legacy suites (`filter.test.js`, `prepare.test.js`, `email_filters.test.js`) pass unchanged — 1639/1639 across the full tree. **Phase 2 follow-up** (per RFC 040 §4) after one production release: delete the shim translators, inline `evaluateJob` calls into `checkJob` / `filterJobs` / `applyPrepareFilter` / `isLevelBlocked`, remove `isLocationBlocked` export.

- **`check_cli_args_sync.js`: pre-commit gate for per-flag + literal-enum drift (warn-mode)** (BL-104 / [RFC 041](rfc/041-cli-args-enum-drift-gate.md), 2026-05-19). New `scripts/check_cli_args_sync.js` plus integration in `.git-hooks/pre-commit` and `.github/workflows/test.yml` close the BL-80-class gap that BL-97 (CHANGELOG-required) and BL-98 (KNOWN_COMMANDS↔cli.md) leave open: those gates pass at command-name granularity, neither catches a removed enum value or an undocumented flag inside a kept command. Per-command code-side parse pulls flag literals from four regex shapes (`args["--foo"]`, `argv.includes("--foo")`, `--foo` in stderr/help template literals, plus the `prepare flags:` blocks inside `engine/cli.js` HELP_TEXT) and enum values from three shapes (`m !== "a" && m !== "b"` inequality chains, `VALID_MODES = [...]` named-array literals, `(valid: a, b, c)` stderr hints); doc-side parse reads the synopsis line and the first pipe-table column under each `### <cmd>` heading in `docs/reference/cli.md` (unescaping `\|` in table cells). Disagreement between two code-side enum sources for the same flag is reported as drift (e.g. inequality says `[fresh, topup]` but stderr hint says `[fresh, topup, weak-fallback]` — the BL-80 leftover shape). Findings render per-command with `flag mismatch:` / `enum mismatch on --X:` / `in-file disagreement on --X:` sections. Pre-commit scoping mirrors BL-98: gate runs only when at least one of `engine/cli.js` / `engine/commands/*.js` (excluding tests) / `docs/reference/cli.md` is in the staged diff. Exit codes: 0 pass, 1 drift (block), 2 heuristic warning (`enum-not-detected` for flags whose enum the gate couldn't statically determine). Escape hatch — any line containing `// cli-args-gate-ignore` is skipped by every code-side regex; the gate tallies hatch usage per command at the end of its run so the hatch can't quietly grow. Cross-command references like `` `validate --dedup` `` inside `engine/commands/prepare.js` are stripped before flag-detection so they don't get attributed to prepare. Globals (`--profile`, `--dry-run`, `--apply`, `--verbose`, `--help`) are exempt from per-command drift since they're documented per-command but referenced from `engine/cli.js` parseArgs. **Warn-only first release**: ships with `CLI_ARGS_GATE_MODE=warn` as the in-code default for this commit per RFC 041 §7 — drift still prints the full structured report to stderr but exits 0 instead of 1 so the gate cannot wedge work mid-migration. Override either way with the env var (`CLI_ARGS_GATE_MODE=block` to force-fail locally; `=warn` after the follow-up flips the default). CI surfaces exit 2 as a `::warning::` annotation and never as a job failure. The block-mode flip lands as an immediate follow-up commit per RFC 041 §7. CI step is named `Check CLI args sync` and sits between `Lint` / `Format check` and `Run tests`. Baseline pass: ran the gate against the current tree (after RFC 034 / BL-80 cleanup). All three classes of false-positive uncovered during the baseline pass were resolved inside the gate, not by editing engine/docs — (1) cross-command refs (`run \`validate --dedup\``, `\`prepare --phase pre\``) inside one command's stderr text were leaking into that command's flag-set; resolved by the `stripCrossCommandRefs` helper that blanks any `<other-cmd> --flag` span before regex; (2) `//` and `/* */` comments full of prose flag mentions; resolved by `stripComments` (preserves line indexes for nearestFlag); (3) the `scan` command paragraph in HELP_TEXT mentions `--no-sync` in the top-level `Commands:` list rather than under a `scan flags:` heading; resolved by extending `helpTextSliceForCommand` to also harvest the command's Commands: paragraph. After tuning, exit 0 in block mode against the live tree; the prepare.js intentional rejection branch for `--mode "weak-fallback"` (RFC 034 migration hint) is preserved verbatim and does not surface as drift because the bareword `weak-fallback` is correctly distinguished from a `--weak-fallback` flag literal. Tests: `scripts/check_cli_args_sync.test.js` covers all 10 cases from RFC §4 plus per-regex positive + negative tests for every entry in the `HEURISTICS` block, plus a baseline regression that runs the gate against the live tree and asserts clean. **BL-104 stays open** until the block-mode flip commit lands. 1571/1571 tests pass.

- **Structured JD extract + pre-SKILL `hard_blockers` + title-encoded geo pre-reject** (BL-89 / [RFC 039](rfc/039-structured-jd-hard-blockers-title-geo.md), 2026-05-19). Closes the audit-2026-05-18 biggest token-burn finding: raw JD prose shipped to the SKILL on every batch row, Python-required roles landing in Notion as `Weak`, and `"Senior PM (UK/EU/India)"` flowing past the locations-based geo filter. Three engine changes, all deterministic, all invisible to the SKILL by design. **`engine/core/jd_extract.js`** gains `extractJDStructure(rawJDText) → { requirements, responsibilities, salary_text, location_text, full_text_excerpt }` — heading-driven heuristic split (case-insensitive matcher table per RFC 039 §3.1: `Requirements/Qualifications/What you'll need/Must-haves/Minimum qualifications` + `Responsibilities/What you'll do/Day-to-day/In this role/You will`; bullet detection on `-/•/*/–`; ≤25 entries × ≤200 chars per array with longest-drop-first when over cap; `full_text_excerpt` = first 3000 chars of the normalized body as deterministic fallback). Heading-shape gate (ends with `:` OR short and free of mid-line `,.—–`) prevents prose like `"Remote — US only."` from re-firing as a heading. The legacy `extractFromJd(jdText) → { schedule, requirements }` wrapper is preserved bit-identical for external callers (Lilia healthcare summary path). **`engine/core/hard_blockers.js`** (new) exports `findHardBlockers({ structuredJD, profile, title }) → string[]` — codes are `required_skill_excluded:<skill>` (regex hits on `structuredJD.requirements[]` joined with newlines + ±3-line co-occurrence with `\b<n>+? years\b` ≥ `min_years` OR a strong marker `required/must have/strong/expert/proficient`, explicitly excluding `nice to have/a plus/preferred/bonus/ideal`), `years_required_max_exceeded:<n>` (when JD requires more years than `hard_blockers.years_required_max`), and `cert_required:<cert>` (substring deny list with word boundaries). Multi-code support: first code in `reason`, full list in `reasons[]`. Missing/empty config → `[]`. Malformed regex patterns are skipped without throwing. **`engine/core/geo_enforcer.js`** gains `extractTitleGeo(title) → { excluded, marker }` and `titleMentionsCandidateGeo(title, profileGeo)` — code-table v1 `TITLE_GEO_PATTERNS` matches parenthetical region tags (`(UK)`, `(EU)`, `(EMEA only)`, `(UK/EU/India)`), inline phrases (`EMEA only`, `APAC only`, `Europe only`, `UK only`, `EU only`, `LATAM only`, `India only`), and `Remote - <region>` patterns. Inclusive-wins composition: a US marker (or any `accept_countries[]` value) anywhere in the title overrides the exclusive marker, mirroring BL-24. **Wiring** in `engine/commands/prepare.js`: title-geo runs inside `applyPrepareFilter` immediately before `enforceGeo` (restrictive modes only — Jared `unrestricted` parity preserved), so doomed rows never reach the URL-check budget; hard-blockers run AFTER JD-fetch and BEFORE `buildBatchEntry` via new `applyHardBlockers(aliveResults, jdByAppKey, profile)` helper, so blocked rows hit `skipped[]` with full `hard_blocker:<code>` reason and get archived via the RFC 035 path (`status="Archived"` + `skip_reason="hard_blocker:..."` in TSV, never pushed to Notion). `buildBatchEntry` attaches `entry.jdStructure = extractJDStructure(jdText)`; `entry.jdText` stays emitted for one release for back-compat (RFC 039 §5). **`engine/core/skip_reasons.js`** adds `geo_title_excluded` to `ENGINE_SKIP_REASONS` and a `hard_blocker:*` wildcard family via the new `isEngineSkipReason(reason)` predicate (literal Set membership OR `hard_blocker:<non-empty>` prefix); `archiveSkippedRows` switched to the predicate so multi-code rows archive cleanly. **SKILL.md Step 2** mentions `jdStructure` as the preferred read field with `jdText` as one-release fallback. **`profiles/_example/filter_rules.example.json`** adds a synthetic `hard_blockers` block with placeholder `ExampleSkillX` + `years_required_max: 15` + empty `cert_blockers[]`. **Architectural invariant**: a row that returns a non-empty array from `findHardBlockers` NEVER reaches the SKILL, NEVER gets a `fit_score`, and NEVER lands in Notion — closes the `feedback_pipeline_fit_score_arch` memory rule at the code level. **Tests** (RFC 039 §4): `engine/core/jd_extract.test.js` +13 (heading variants, all four bullet leaders, bullet cap longest-drop-first, length cap, inline salary, empty input, 3000-char excerpt cap, back-compat shape); new `engine/core/hard_blockers.test.js` (16 cases: skill+years co-occurrence, "nice to have" not firing, framework pattern alternates, years_required_max, cert blockers with word boundary, multi-code, no-config → `[]`, malformed regex tolerance, pure-input isolation, ±3-line co-occurrence); `engine/core/geo_enforcer.test.js` +18 (each `TITLE_GEO_PATTERNS` entry, plain-title pass, inclusive-wins composition, multi-region exclusive, `accept_countries` matching); `engine/commands/prepare.test.js` +7 (`jdStructure` emitted on every row with JD body / absent without, hard-blocker row in `skipped[]` not `batch[]`, hard-blocker rows never carry `fit_score`, title-geo archived without JD fetch attempted, inclusive US wins, ENGINE_SKIP_REASONS guard updated for `geo_title_excluded` + predicate-based `hard_blocker:*` acceptance, SKILL.md contract assertion). `npm test`: 1570/1570 across engine + SKILL contract suites.

- **Engine emits `Archived` for filter-skipped rows directly (closes RFC 034 archive gap)** (BL-91 / [RFC 035](rfc/035-engine-emits-archive-for-skipped.md), 2026-05-18). After RFC 034 removed `decision` from the SKILL output schema, filter-skipped rows had no path to `Archived` — they stayed `Inbox` forever and the blocklist's effect was invisible until you grepped `prepare_context.json`. `engine/commands/prepare.js` `runPre` (and `runPreTopup` for new skips only — carryover was archived by the prior run) now writes `status="Archived"` + `skip_reason=<canonical>` directly to the TSV at pre-phase, before `prepare_context.json` is written; **Notion is not touched** (these rows never had a Notion page — RFC 014 invariant). Canonical enum in new file `engine/core/skip_reasons.js` exports `ENGINE_SKIP_REASONS` (`company_blocklist` | `title_blocklist` | `title_requirelist` | `company_cap` | `geo_no_location` | `geo_blocklist` | `geo_metro_miss` | `geo_country_miss` | `geo_remote_only_miss` | `geo_unknown_mode` | `url_dead`) + `ALREADY_EVALUATED_REASONS` (`already_evaluated_weak` | `already_evaluated_duplicate`; surfaced for SKILL context only, no TSV write because the rows already carry their verdict). New helpers `archiveSkippedRows` + `formatArchiveBreakdown` in `prepare.js`. **First-archive-wins** (§6.1): already-`Archived` rows with a non-empty `skip_reason` are never overwritten — preserves the scan-time reason (e.g. `location_blocklist` from BL-24) when a later prepare hit would emit something less informative (`company_cap`). Added four columns to persist Claude's fit verdict per row: `fit_score` (`Strong` / `Medium` / `Weak`), `fit_rationale`, `fit_evaluated_at`, `skip_reason` (SKILL-level only: `weak_fit` / `duplicate`). Subsequent `prepare` runs will skip already-evaluated rows instead of re-paying the SKILL cost. Auto-upgrade on read from v1 / v2 / v3 with empty fit columns; writes always emit v4. Engine-level skips (company cap, blocklists, geo) continue to be recomputed each run and are not persisted. See [docs/reference/tsv-schema.md](docs/reference/tsv-schema.md).
- **`prepare --phase pre` skips already-evaluated rows** (BL-9, 2026-05-05). New filter step runs before `applyPrepareFilter`: rows with `fit_score=Weak` or `skip_reason ∈ {weak_fit, duplicate}` no longer reach URL-check / JD-fetch / SKILL judgement. They appear in `prepare_context.json` `skipped[]` with reasons `already_evaluated_weak` / `already_evaluated_duplicate` and a new `stats.alreadyEvaluated` counter. Dramatically reduces token cost on repeat runs once fit verdicts have been persisted.
- **`prepare --phase commit` persists fit verdict for every decision** (BL-9, 2026-05-05). SKILL results JSON now carries `fitScore` / `fitRationale` / `skipReason` on every result (`to_apply` / `skip` / `archive`). Engine writes them to TSV columns `fit_score` / `fit_rationale` / `skip_reason` and stamps `fit_evaluated_at = now` whenever a `fit_score` is present. Validators reject invalid values (`fitScore` must be Strong/Medium/Weak; `skipReason` must be weak_fit/duplicate) with a stderr warning instead of corrupting the column. Stdout summary surfaces `fitWritten` count. Downgraded-to-skip rows (invalid resumeVer) still capture the verdict so they are not re-evaluated next run.
- **`prepare --phase pre --mode topup`: two-pass batch refill** (BL-9, 2026-05-05). `--phase pre` now runs in two modes. `--mode fresh` (default) preserves the original behavior **and** persists the unconsumed (still-eligible) tail of the filter pipeline as `deferredQueue[]` (an array of TSV keys) on `prepare_context.json`. `--mode topup` reads the existing context, pulls the next `--need K` keys from the queue, re-validates them against the current TSV (drops keys that have moved out of Inbox, gained `fit_score=Weak`, or now fail `applyPrepareFilter` after rule changes), URL-checks + JD-fetches the residue, and **appends** new entries to `batch[]`. Counters (`urlChecked` / `urlAlive` / `urlDead` / `alreadyEvaluated` / `topupRuns`) accumulate across runs; `skipReasons` is recomputed from the merged `skipped[]`. Use this after a SKILL run where Strong + Medium fell below `batchSize` so the next operator turn picks up where the last one left off without a fresh scan. New CLI flags: `--mode <fresh|topup>` (default `fresh`), `--need <k>` (default = `batchSize - len(currentBatch)`).
- **`prepare` autonomous loop with priority Strong→Medium→Weak** (BL-9 Step 5, 2026-05-05). The user invokes `/job-pipeline prepare` once; the SKILL orchestrates a multi-iteration loop until 30 jobs land in Notion or the Inbox is exhausted. Engine: new `--mode weak-fallback --need K` reads `deferredQueue` plus already-Weak fresh-Inbox rows in TSV; entries get `wasAlreadyWeak: true` + `priorFitScore` + `priorFitRationale` so the SKILL reuses the saved verdict instead of re-judging. `filterAlreadyEvaluated({mode:"weak-fallback"})` keeps Weak rows; `duplicate`-flagged rows are still always dropped. Engine: new `stats.inboxExhausted: bool` written by all three modes (fresh / topup / weak-fallback) — true when no more fresh rows exist in TSV outside the current batch (excluding duplicates; in non-weak-fallback modes, already-Weak rows still count as not-exhausted). SKILL.md `prepare` section rewritten as autonomous loop spec: max 3 iterations of `topup` chasing Strong (loop stops only on Strong ≥ 30 / iter ≥ 3 / `inboxExhausted` — Mediums never satisfy the target since selection is sequential Strong→Medium→Weak), then `weak-fallback` to fill the rest if Strong+Medium still short, then push top-30 to Notion in priority order. Step 9 (Notion push) and Step 10 (results.json) now run ONCE on the final top-N list, not per iteration. Step 5 reframed as bucket-assignment (verdicts.strong / medium / weak) — final to_apply / skip is decided in the loop's selection phase, not per job.
